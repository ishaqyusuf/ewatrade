# Service Commerce Compatibility And Contraction Inventory

## Purpose

This inventory is the switch and rollback source of truth for Service Commerce.
It distinguishes authoritative vertical records, shared canonical commerce,
compatibility adapters and historical-only persistence. Nothing in this file
authorizes production traffic, provider execution, schema contraction or
deletion.

`Shared` means the generic boundary is canonical. `Both` means a shared seam
coexists deliberately with a vertical owner. `Legacy history` means new runtime
writes have stopped but retained rows still require reconciliation.

| Control | Current evidence | Release status |
| --- | --- | --- |
| Store capability activation/deactivation | `serviceCommerce.setActivation` delegates to `packages/db/src/queries/service-commerce-access.ts`; policy and readiness are re-evaluated transactionally. | Executable per Store. Suspended profiles fail closed. |
| WhatsApp Store/Connection suspension | Binding suspension and Connection lifecycle commands live in `whatsapp-connections.ts`; inbound claim and outbound dispatch reauthorize. | Executable per binding/Connection. Not a platform-wide provider freeze. |
| Pharmacy operational stop | Prescription Store activation, policy decisions and incident/privacy controls remain source-owned. | Executable within their exact regulated scopes. |
| Report release cohort | The report route and tRPC procedures are role-gated but have no Store cohort or feature switch. Profile deactivation does not remove historical reporting. | No runtime cohort control. Withdraw only through an approved application deployment rollback, or implement a separately reviewed report-release control. |
| Shared-versus-compatibility route selector | Both router families remain registered and callers choose their explicit route. | No central runtime selector. Rollback means redeploying the preserved compatibility caller/artifact. |
| Tenant/Store all-jobs freeze | Individual jobs reauthorize against policy/profile/source facts; Trigger task registration is global. | No unified scoped freeze. Pause exact tasks at the job platform or add a reviewed scoped kill switch before claiming this control. |
| Payment/media/OCR/courier provider freeze | WhatsApp has binding/Connection suspension. Payment, production media/safety/OCR and manual courier do not share one provider lifecycle. | No unified kill switch. Each authorized provider canary must name its own stop/rollback action. |

## Switch Preconditions

Before any production traffic switch, record:

1. the selected Store cohort and the exact current/target application artifact;
2. production migration fingerprint/status and immutable-history census;
3. every compatibility reader and writer still observed in that cohort;
4. live provider canary owner, time window, safe evidence reference and exact
   stop action;
5. the observation window and approved performance/rate thresholds;
6. the rollback operator and whether rollback is an in-app control, provider
   suspension, job-platform pause or prior-artifact deployment; and
7. owner authorization for the switch only, explicitly excluding contraction.

## Contraction Preconditions

Contraction is a later, separate decision. Every candidate must have zero
runtime readers, zero runtime writers, reconciled immutable history, a retained
reader for required records, passing cross-vertical and Pharmacy compatibility
evidence, a reversible application artifact and explicit owner approval. A
physical model rename, route/export deletion or job removal is prohibited while
any row, queued job, public token, rollback path or legal/retention duty still
depends on it.
